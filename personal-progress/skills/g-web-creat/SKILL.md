# 创建并发布个人网站或软件

从产品意图开始，持续执行到可验证的正式版本。优先沿用现有项目的技术栈、组件和工程约定，避免无必要地增加依赖。

## 1. 明确结果

1. 将需求判断为新产品、功能、缺陷修复、数据迁移、外部集成或部署任务。
2. 把用户文字、截图和示例整理成可以实际观察和验证的验收标准。
3. 区分必须实现的行为与可选的视觉优化。
4. 仅在选择会显著影响数据归属、费用、安全或产品行为时提问；其他情况采用保守假设并继续执行。

## 2. 修改前检查项目

1. 阅读仓库说明、依赖清单、页面路由、相关组件、数据模块、环境变量示例和部署配置。
2. 检查工作区状态，保留用户已有且与当前任务无关的修改。
3. 追踪完整数据链路：用户操作 -> 输入校验 -> 本地存储或 API -> 云端同步 -> 页面展示。
4. 判断问题实际发生在浏览器、前端代码、服务端接口、数据库、第三方服务还是部署域名层。

## 3. 先设计数据，再制作界面

先确定每类数据保存在哪里：

- 组件状态：只保存当前操作的临时信息。
- 浏览器存储：支持本机和离线使用，但不会天然跨设备同步。
- 账号数据库：保存用户历史记录并支持跨设备访问。
- 服务端密钥：用于凭证和高权限操作，严禁暴露给浏览器。

在实现前确定稳定 ID、更新时间、修改和删除规则、去重方式、旧数据迁移及合并规则。修改数据结构时保留现有记录。不得为了修改一个账号而给所有用户写入同一份私人数据。

## 4. 按完整使用路径实现

每次完成一条端到端路径：

1. 新增或修改领域数据与存储接口。
2. 将页面交互连接到该接口。
3. 根据实际流程补齐空状态、加载、禁用、校验、保存成功、编辑和错误状态。
4. 为控件提供清楚标签和有效反馈。
5. 验证刷新、页面切换、自动保存、账号同步和旧记录兼容性。

维护已有产品时，除非用户明确要求重新设计，否则保持原布局和视觉语言。优先使用项目现有组件与图标。

## 5. 明确处理外部集成

处理登录、通知、机器人、图片上传或 AI 功能时：

1. 区分浏览器能力和服务端能力。
2. 只在服务端保存密钥；可以说明环境变量名称，但不得输出密钥值。
3. 检查第三方权限、回调或事件地址、签名配置和正式环境 URL。
4. 为缺少配置或权限被拒绝提供用户能直接处理的提示。
5. 先单独测试外部服务，再判断是否为页面问题。

## 6. 根据风险进行验证

先运行针对性测试，再运行生产检查。Windows 上的 Node.js/TypeScript 项目可执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/verify-project.ps1 -ProjectPath <项目路径>
```

从本 Skill 调用时，使用其自带的 `scripts/verify-project.ps1`。修复本次修改造成的错误；对于无关的既有警告，只做说明，不进行大范围重构。

同时手动检查被修改的使用路径。视觉改动需要检查桌面端和手机端；数据改动需要检查新增、修改、删除、刷新和旧数据兼容。

## 7. 发布并确认正式版本

仅在用户要求发布，或当前项目的既定流程明确包含发布时进行部署。

使用 Vercel 时：

1. 先完成本地生产构建。
2. 执行 `npx vercel --prod --yes`。
3. 记录新部署的域名和部署 ID。
4. 执行 `npx vercel alias set <新部署域名> <正式域名>`，明确绑定正式域名。
5. 执行 `npx vercel inspect <正式域名>`，确认部署 ID 与新版本一致。

如果项目曾出现正式域名仍指向旧版本的问题，不得只把部署日志中的 `Aliased` 当作发布成功证明。

## 8. 清楚交付结果

先说明用户能够看到和使用的结果。完成发布时提供正式链接，同时说明通过的检查和剩余限制。只有用户仍需亲自操作时，才提供额外操作步骤。

## 非网站软件

桌面、移动端、自动化工具和其他软件沿用相同顺序：明确结果 -> 检查项目 -> 设计数据 -> 完整实现 -> 测试 -> 打包 -> 发布 -> 验证。将浏览器和 Vercel 检查替换为对应平台的打包、签名、安装和冒烟测试。
